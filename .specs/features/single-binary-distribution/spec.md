# Single-Binary Distribution Specification (#236)

## Problem Statement

`npx verchestra` is the only way to get Verchestra today, and it needs npm and
an ambient Node for bootstrap. Locked-down and air-gapped machines often have
neither. Issue #236 asks for one executable per supported target. Each
executable embeds the pinned Node 24.14.0 runtime and runs the same hermetic
TUF activation the npx launcher drives, with no dependency on an ambient Node,
even for bootstrap.

The owner decided on 2026-09-29 to build it now. The signed 1.0.0 hold
(`docs/qualification/release-decision-1.0.0.md`) stays as it is. Nothing here
promotes a release or claims release readiness.

## Goals

- Ship one executable per fleet target: `darwin-arm64`, `darwin-x64`,
  `linux-arm64`, `linux-x64`, and `win32-x64`.
- Embed the pinned official Node runtime, verified against digests recorded
  from nodejs.org.
- Build deterministically, and emit a manifest that names every byte and its
  license.
- Add no dependency.

## Out of Scope

| Item | Reason |
| --- | --- |
| Publishing, uploading, or promoting any binary | Owner step. The workflow produces artifacts only. |
| Developer ID signing, notarization, Authenticode signing | Owner actions on the emitted bytes. See `design.md` § Code signing. |
| Signed provenance attestations per artifact | Needs an owner-held identity. Recorded as pending in the qualification report. |
| `win32-arm64` | It is in the launcher's host set but not in the qualified fleet. No T76 closure exists for it. |
| Changing T76, T77, or the 1.0.0 decision | This is a separate qualification surface. |

## Requirements

| ID | Requirement |
| --- | --- |
| SBD-01 | WHEN a binary is built for a target THEN the embedded runtime SHALL be the official Node 24.14.0 executable for that target, and SHALL be accepted only if its digest equals the pin in `apps/vestra-launcher/single-binary/node-runtime.json`. That pin was recorded from `SHASUMS256.txt`. The builder SHALL NOT download anything. |
| SBD-02 | The SEA blob SHALL be generated by the pinned runtime's built-in `--experimental-sea-config`, and injected without any new dependency. The build SHALL refuse to emit an executable whose blob cannot be recovered by the runtime's own lookup rules. |
| SBD-03 | WHEN two builds run on the same host from identical inputs THEN every emitted file SHALL be byte-identical. |
| SBD-04 | The build SHALL emit a manifest recording: <br>• the target; <br>• the digest, format, and signature state of the executable; <br>• the Node version, the pins digest, and the archive and executable digests; <br>• the launcher bundle digest; <br>• the SEA settings and the blob and asset digests; <br>• the license files; <br>• a CycloneDX 1.5 SBOM that names every bundled third-party package. <br>The manifest SHALL contain no machine-local path. |
| SBD-05 | The binary SHALL run the npm launcher's bootstrap, composed from the same `runBootstrap`, `NodeActivationClosure`, and `machineLocalEnvironment`. Its pinned inputs SHALL be embedded and validated by the same `readPinnedInputs` contract. |
| SBD-06 | Every argument vector SHALL reach the activated release verbatim, with one exception: a lone `--version`, which SHALL be answered from the validated embedded inputs without activating anything. |
| SBD-07 | The binary SHALL depend on no ambient `node`. It SHALL run with `PATH` empty, ignore `NODE_OPTIONS`, and resolve only Node built-ins at run time. |
| SBD-08 | The build SHALL fail closed on each of these, and a refused build SHALL leave no output behind: <br>• an unsupported target; <br>• an ambiguous or missing runtime; <br>• a runtime digest mismatch; <br>• inputs the launcher would refuse; <br>• an existing output directory; <br>• any executable layout the injector cannot explain. |
| SBD-09 | macOS binaries SHALL carry a reproducible ad-hoc signature. Windows binaries SHALL carry no stale Authenticode signature. Identity signing and notarization SHALL be documented as owner actions. |
| SBD-10 | A manual, read-only workflow SHALL build and test all five targets on native runners, with SHA-pinned actions, no publication, artifacts only, and zero skipped cases. |
| SBD-11 | A qualification document SHALL state what is proven locally and what is still pending. |
| SBD-12 | No status surface SHALL claim 1.0, promotion, or production readiness. |

## Acceptance Criteria

1. WHEN the host target's pinned archive, or the pinned official runtime, is
   available THEN `tests/build/vestra-binary.test.mjs` SHALL build the host
   binary twice with identical results.
2. WHEN that binary runs with `PATH=""` and a hostile `NODE_OPTIONS` THEN
   `--version` SHALL print the launcher version and exit 0.
3. WHEN that binary runs with `PATH=""` and any other arguments THEN it SHALL
   reach the TUF activation path: it SHALL anchor the embedded, signed fixture
   root under the redirected home and dial the pinned source.
4. WHEN neither the pinned archive nor the pinned official runtime is
   available THEN the host-build cases SHALL be skipped, and SHALL state that
   reason. On every CI runner the running Node is the official binary, so
   nothing is skipped there.
5. Cross-target builds SHALL be exercised in
   `.github/workflows/single-binary-build.yml`.

## Open Decisions

- **Is a local `--version` the right difference between channels?** The npm
  channel passes `--version` through to the activated CLI, which also reports
  the release digest. The single binary answers it locally, so it works before
  any activation. The owner may prefer strict parity. That would move the
  launcher's own version to a flag the product CLI does not use.
- **Six targets or five?** `.specs/features/milestone-2-completion/analysis.md`
  speaks of "six SEA artefacts". Issue #236 and the qualified fleet name five.
  This change builds five.
- **Is the injector the right long-term choice?** Once the pinned Node moves to
  a release with `--build-sea`, the in-repository injector can be retired in
  favor of Node's own. That needs a runtime re-qualification, not a silent
  swap.
