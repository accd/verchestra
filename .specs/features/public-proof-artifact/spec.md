# Public Proof Artifact Specification

Issue: #155

## Problem Statement

The public site and README explain Execution Packages, Run Capsules, and
signed Handoffs conceptually, but a visitor can never inspect a real one:
every page under `apps/site/src/content/docs/` is prose, and
`apps/site/public/` holds only a favicon, robots.txt, and a social card.
The strongest available honesty upgrade is one real artifact, not more
copy. The 2026-08 Plan Mode audit classified this as the top actionable
P1 product gap (finding F1) and the owner approved an Execution Package
fixture as the first artifact, subject to this specification's review.

## Objective

One real, deterministic, regenerable Execution Package produced by
repository code from a qualified fixture, published on the site as an
inspectable page and linked from the README — with an integrity test that
makes silent rot impossible.

## Scope

- One Execution Package generated from an existing deterministic fixture.
- One site page that renders the artifact for inspection.
- A committed regeneration script or command.
- A drift/integrity test binding the published bytes to the generator.
- One README link from the existing "What works today" surface.

## Non-goals

| Exclusion                                  | Reason                                  |
| ------------------------------------------ | --------------------------------------- |
| Live execution or a new CLI command        | Public CLI stays `init` until the chain |
| Run Capsule and Handoff samples            | Follow-up once the pattern is proven    |
| Any visual redesign of the site            | The gap is proof, not design            |
| Marketing claims derived from the artifact | The artifact speaks for itself          |

## Requirements

1. **PRF-01** — WHEN the artifact is produced THEN it SHALL be generated by
   tracked repository code from a deterministic fixture, never hand-written,
   and the exact generator entry point SHALL be named in the page.
2. **PRF-02** — WHEN the artifact is published THEN it SHALL contain zero
   secrets, credentials, machine-local paths, personal identities, or
   production data, enforced by the existing prohibited-content checks.
3. **PRF-03** — WHEN a visitor reads the page THEN the artifact SHALL be
   labeled as fixture-generated, not live execution, in the first screen of
   content, with the missing stages named explicitly.
4. **PRF-04** — WHEN a contributor wants to reproduce it THEN one documented
   command SHALL regenerate byte-identical output from a clean clone.
5. **PRF-05** — WHEN the committed artifact and the generator disagree THEN a
   test SHALL fail naming the divergence cause specifically (not only an
   error code), and the site build SHALL not publish the stale bytes.
6. **PRF-06** — WHEN the page renders THEN it SHALL be readable in light and
   dark themes and SHALL not require client-side runtime APIs.

## Acceptance Criteria

Each requirement maps one-to-one: PRF-01/04/05 to a unit test around the
generator plus a drift test comparing committed output against regeneration;
PRF-02 to the existing secret/path scanners extended over the artifact file;
PRF-03/06 to `apps/site/scripts/check-built-site.mjs` render assertions and
the existing site theme tests. A discrimination sensor must tamper one byte
of the committed artifact and observe the drift test fail with the specific
divergence message, then restore and pass clean.

## Architecture

The artifact is a build-time projection: canonical source is the fixture and
generator inside the product packages; `apps/site` only renders committed
output. No new package, no inward-dependency change, no runtime coupling —
the site never imports product packages at page-render time. NestJS: not
applicable. Design-phase work will bound exactly where the generator lives
and how the site consumes the committed file.

## Safety and Authority

The artifact is untrusted display data on the page; nothing executes it.
Generation runs only at development time via the documented command, never
in CI deploy steps, so the published bytes are always reviewed bytes.

## Verification

`pnpm site:check`, `pnpm site:test`, `pnpm site:build`, plus `pnpm
gate:quick` and the new unit/drift tests. Sensor evidence recorded before
any validation claim.

## Dependencies and Open Decisions

No hard dependencies; independent of the T69 stream. Open for owner review
of this spec: which fixture seeds the package (recommendation: the
cross-backend delivery-proof fixture, already qualified), and the site route
name.
